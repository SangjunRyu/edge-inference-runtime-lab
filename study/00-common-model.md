# 00 — 다섯을 묶는 공통 모델

프레임워크를 다섯 개 배우면 어휘가 다섯 개 생긴다. 그 밑의 모델을 먼저 잡으면
사례가 다섯 개 생긴다. 이 문서가 그 모델이다. **C++이 아니라 큐잉 이론이다.**

## 리틀의 법칙

```
L = λ × W

L = 시스템 안에 있는 항목 수 (in-flight, resident)
λ = 처리율 (throughput)
W = 항목 하나가 시스템에 머무는 시간 (latency)
```

이미 이 프로젝트에서 관측했다. W2의 in-flight 깊이 스윕에서 `resident`가 깊이를
그대로 따라갔다. 6.96 → 29.65로 깊이 1에서 16까지다. 처리량은 383에서 386으로
거의 안 변했으니, 법칙에 따라 **지연이 그만큼 늘어야 하고 실제로 늘었다.**
E2E p50이 25.8에서 74.1 ms가 됐다.

**실무적 결론 셋.**

1. 처리량이 포화한 뒤에 in-flight를 늘리면 **지연만 산다.** W2 무릎이 4였던 이유다.
2. 세 값 중 둘을 재면 나머지가 나온다. 재기 어려운 것을 계산으로 얻을 수 있다.
3. 상주 프레임 수를 재는 것은 지연을 재는 것과 같은 정보다. 다만 상주 수는 개수라
   기계가 흔들려도 살아남는다. **W5가 개수로 옮긴 이유가 여기 있다.**

## 유한 큐는 지연 증가를 손실로 바꾼다

무한 큐 앞에서 소비자가 생산자보다 느리면 지연이 무한히 자란다. 유한 큐에서는 자랄
곳이 없으니 정책이 개입한다. 그 정책이 손실의 종류를 정한다.

```
막기(Block)      생산자가 느려진다 → 소스가 시계를 가지면 신선도를 잃는다
오래된 것 버리기  지연이 유계로 유지된다 → 프레임을 잃는다
새 것 버리기      지연이 유계이지만 적체에서 공급한다 → 더 상한 프레임을 낸다
```

W5-4가 잰 표가 정확히 이것이다. 네 정책이 같은 40 FPS를 냈고, `block`의 p95 나이가
1,921 ms 대 `drop-oldest`의 100 ms였다. **처리량은 정책이 아니라 워커가 정한다.
정책은 누가 버려지는지를 정한다.**

## 천장은 자원과 구조의 최솟값이다

```
C_resource   = 풀에 있는 슬롯 수
C_structural = S + ΣQi + ΣWj   (소스 + 큐 용량 합 + 워커 수 합)
ceiling      = min(둘)
```

**공식은 법칙이 아니라 생명주기의 성질이다.** 프레임이 어느 리스를 언제까지 쥐는지가
바뀌면 식이 바뀐다. W5-2가 이걸 세 번 틀리고 세 번 repro로 남겼다.

## 포화 근처에서 p95가 폭발한다

대기열 이론의 기본 결과다. 이용률 ρ에서 대기 시간이 대략 `ρ / (1 - ρ)`로 간다.
ρ가 0.9면 9배, 0.95면 19배다. **평균만 보면 완만한데 꼬리는 절벽이다.**

이 프로젝트의 규약 2번(맨 평균 금지, p50/p95/max 병기)이 이 사실에서 나온다. 그리고
W2 발견 H에서 Arc GPU가 398초 멈춘 걸 p50만 봤으면 못 봤을 것이라는 문장도 같은
이야기다.

## 대기 시간과 서비스 시간은 다른 것이다

측정에서 가장 자주 무너지는 구분이다. 하나의 타이머로 둘을 감싸면 큐가 깊어질수록
"계산이 느려진 것처럼" 보인다.

세 시스템이 같은 방식으로 인정한다.

| 시스템 | 분리 방법 |
|---|---|
| DX-RT | `get_latency()` 와 `get_npu_inference_time()` 을 따로 노출 |
| Triton | `nv_inference_queue_duration_us` 와 `nv_inference_compute_infer_duration_us` 메트릭 |
| GStreamer | latency query 로 파이프라인 지연을 따로 질의 |

내 하네스는 아직 안 나눴다. `handoff/open-threads.md`의 미해결 항목이고, W2에서
`inference` p50이 깊이 1에서 16까지 3.52 → 36.27 ms로 열 배가 된 이유다. **장치가
느려진 게 아니라 대기가 측정 구간 안으로 들어온 것이다.**

## 확인할 질문

읽고 나서 이 질문들에 숫자나 코드 위치로 답할 수 있으면 이 문서는 끝난 것이다.

1. 내 W2 깊이 스윕 데이터로 리틀의 법칙이 성립하는지 계산할 수 있나.
   `resident ≈ throughput × E2E` 를 저장된 결과로 확인해 보라. 기계 시간 0이다.
2. 내 파이프라인에서 이용률 ρ를 어떻게 정의할 것인가. 병목 스테이지의 서비스 시간
   대비 도착 간격인가.
3. `unaccounted` 는 대기인가 서비스인가. 규약이 "크면 가장 먼저 설명할 값"이라고
   적어뒀는데 아직 설명하지 않았다.
4. 내 스케줄러에서 대기와 서비스를 나누려면 어디에 타이머를 넣어야 하나. 큐에서
   꺼낸 시각과 스테이지 진입 시각이 이미 있나.

## 참고

- 리틀의 법칙은 분포 가정이 없다. 정상 상태이기만 하면 된다. 그래서 합성 워크로드에도
  적용된다.
- 이 문서에 수학은 이 이상 필요 없다. M/M/1 대기열 공식을 외울 필요는 없고,
  **포화 근처에서 꼬리가 폭발한다**는 정성적 사실과 리틀의 법칙이면 실무에서 쓸 건
  다 나온다.
