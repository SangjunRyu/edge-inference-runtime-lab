# W4 — 같은 파이프라인을 C++로 명시적으로 쓰면 무엇이 달라지는가

원문: [`docs/findings-w4.md`](../docs/findings-w4.md), 계획서
[`docs/w4-plan.md`](../docs/w4-plan.md), 설치 [`docs/w4-setup.md`](../docs/w4-setup.md)

같은 파이프라인을 명시적 동시성과 메모리 소유권으로 표현할 수 있는지, 그리고 그
통제가 파이썬으로는 닿지 않는 개선을 드러내는지를 묻는다.

## 툴체인 — 마이크로소프트 도구 없이

OpenVINO의 **C** API를 쓴다. C++ API가 아니라 C인 것이 핵심이다. MinGW와 MSVC는
C++ ABI를 공유하지 않아서 MSVC로 빌드된 `openvino.lib`를 GCC에서 링크할 수 없지만,
C는 ABI가 안정적이라 `openvino_c.lib`는 링크된다. MSYS2 UCRT64만으로 빌드된다.

런타임은 프로젝트 자기 venv에서 가져온다. C++ 쪽과 파이썬 쪽이 버전 번호만 비슷한
두 빌드가 아니라 확실히 같은 OpenVINO 빌드가 된다.

## 발견한 결함 셋, 그리고 그중 중요한 하나

W4에서 나온 런타임 결함 셋은 전부 소유권과 수명 문제였고, 지금은 전부
[`repro/`](../repro/README.md)에 실행 가능한 프로그램으로 있다.

- **죽은 콜백 디스크립터를 가리키는 포인터.** `ov_infer_request_set_callback`은
  넘겨받은 포인터를 보관하는데 디스크립터가 스택 지역변수였다.
- **콜백이 유한 큐에서 막혀 교착.** 완료 콜백이 백프레셔를 런타임 자기 스레드에
  적용해서, 런타임이 자기 `wait`와 맞물려 멈췄다.
- **running 상태를 벗어나지 않은 요청을 읽음.** 콜백이 요청이 실행 상태를 떠나기
  전에 발동해서 접근자가 `REQUEST_BUSY`를 반환한다.

첫 번째가 W5 전체의 규칙을 만든 결함이다. `--mode probe`로 확인했다. 런타임에 넘긴
디스크립터를 프로그램이 여전히 소유한 채 변형하고 콜백이 어느 값을 받는지 본다.
미정의 동작이 전혀 없어서 매번 같은 답을 낸다.

```
변형 전에 설정한 인자, 콜백이 받은 값: 0
변형 후에 설정한 인자, 콜백이 받은 값: 1
→ 런타임은 완료 시점에 디스크립터를 읽는다. 포인터를 보관한다.
```

## 재정렬 버퍼는 후처리를 동시에 하는 값이다

수집기가 하나면 순서를 어길 수가 없고 버퍼도 필요 없다. 수집기 넷이면 순서를 벗어난
완료가 96개 생기고, 버퍼를 끄면 **479프레임 중 72개가 잘못된 순서로 나오면서 프레임
개수는 정확히 맞는다.** 총계까지 맞는 조용히 틀린 파이프라인이다.

W4 2단계의 포팅은 순서를 벗어난 완료를 하나도 만들지 못했는데 이유가 구조적이었다.
FIFO 하나를 비우는 수집기 하나는 아무것도 추월할 수 없다. 20번 프레임을 늦추면
21번도 함께 늦는다. 결함에는 동시성이 필요하다.

## 파이썬 오케스트레이션은 순차에서 약 25%, 겹침에서 4% 든다

호스트 스테이지는 어느 쪽이든 C++이 2~10배 빠르다. 겹침은 그것들을 임계 경로에서
치우고, 임계 경로에 없는 비용은 비용이 아니다.

이건 W2 결과 1이 반대 방향에서 도착한 것이다. **겹치는 이유는 호스트가 느려서가
아니라 호스트가 더 이상 중요하지 않게 되기 때문이다.**

## 튜닝 후보 둘 중 하나는 살고 하나는 죽었다

전처리 다섯 패스를 하나로 융합하는 건 실재한다. 1080p에서 B/A 0.61이고 방향이 두 번
독립적으로 확인됐다. 입력 텐서를 프레임마다 감싸지 않고 한 번만 바인딩하는 건
추론을 2% 움직이는데 산포가 25%다. **주변 잡음보다 작아서 지지되지 않음으로
기록했다.**

## 마지막 세션 — 계측기의 결함 셋

마지막에 판정 기준을 고치고 나니 3단계 결론 둘 다 살아남지 못했다. 고친 것은
셋이다.

- **비율이 쌍 안에서 형성되지 않았다.** `median(A 실행들) / median(B 실행들)`이었다.
  숫자 하나라 산포가 없고, 통제 검사가 시험할 대상이 없어 기본 통과했다. 35% 움직인
  기계에서였다.
- **모든 쌍에서 C++이 먼저 돌았다.** 쌍 안의 예열이 매번 한쪽에 청구됐다. 균일하게
  적용한 편향은 쌍 설계로 상쇄되지 않는다.
- **`inference`는 설명된 것 같은 통제가 아니었다.**

고친 기준으로 저장된 쌍을 **기계 시간 0으로** 다시 읽었다.

| 실행 | 대상 B/A | 통제 | 통제 CV | 판정 |
|---|---|---|---|---|
| `--fused` | preprocess **0.61** (CV 45%) | inference 1.09 | **35%** | 통제 실패 |
| `--reuse-tensor` | inference 0.98 (CV 25%) | read 0.98 | **15%** | 통제 실패 |

예전 기준(통제의 *수준*이 1.0 근처인가)으로는 둘 다 통과였다. **수준은 맞고 분산이
깨진 게 정확히 순차 비교에서 배운 실패 양상이다.**

결과는 대칭이 아니다.

- `--reuse-tensor`의 "지지되지 않음"은 살아남고 더 강해진다. 2% 효과 대 25% 분산에
  더해, 통제가 "이 실행은 실재하는 효과도 탐지 못 했다"를 덧붙인다.
- `--fused`의 0.61배는 근거를 잃는다. 방향은 독립 측정 둘과 메커니즘(5패스 → 1패스)이
  받치지만, 숫자를 낸 실행이 기준을 못 넘는다.

`--reanalyse`가 이걸 가능하게 했다. 저장된 쌍에 오늘의 기준을 기계 시간 없이
적용한다. 기준이 전부 실행 **이후에** 고쳐졌기 때문에 중요하다.

## 비동기 융합은 측정이 아니라 계산이 답한다

순차에서는 프레임이 스테이지의 *합*이고, 파이프라인에서는 속도를 *가장 느린*
스테이지가 정한다. 나머지 절약분은 갈 곳이 없다.

NPU 360p, in-flight 4에서 스테이지별 프레임당 서비스 시간이다.

```
read          0.376 ms
preprocess    0.410 ms
inference    15.716 / 4 = 3.929 ms
postprocess   0.018 ms
                          병목: inference, 상한 255 FPS
```

전처리는 병목의 10%다. 절반으로 줄여도 병목은 그대로다.

> **가능한 최대 처리량 이득: ×1.0000**

"대략 1"도 "잡음 안"도 아니다. 전처리가 9.6배 커져야 절반 줄이기가 초당 한
프레임이라도 산다.

1080p는 같은 답인데 이유가 더 흥미롭다.

```
read          1.208 ms
preprocess    0.609 ms
inference     4.935 / 4 = 1.234 ms
```

**read와 inference가 2% 안에 붙는다.** 디코드 병목과 디바이스 병목이 동시다.
전처리가 여기서는 병목의 49%까지 올라오는데도 안 묶이고, 이득은 또 ×1.0000이다.
1080p에서 실제로 도움이 될 건 두 번째 디코더 스레드다.

| 셀 | 전처리 비중 | 0.56배에서 가능한 최대 이득 |
|---|---|---|
| 순차 360p | 합의 2.5% | ×1.011 |
| 순차 1080p | 합의 9.0% | ×1.041 |
| 겹침 360p | 최대값의 10% | **×1.0000** |
| 겹침 1080p | 최대값의 49% | **×1.0000** |

안전한 방향으로 견고하다. inference를 in-flight로 나눈 건 장치가 정말 4중 동시성을
준다는 가정인데, 덜 주면 inference 서비스 시간이 *커져서* 전처리는 병목에서 더
멀어진다.

이 답을 구하려고 돌린 측정들은 애초에 답할 수 없었다. CV 38%와 41%로, 참값이 **0**인
효과를 재고 있었다.

## W4가 내놓은 가장 날카로운 문장

> **순차에서 실재하는 호스트 최적화가 파이프라인이 겹치는 순간 증명 가능하게
> 무가치해질 수 있고, 스테이지 표가 그걸 측정 전에 말해준다.**

파이썬 오케스트레이션은 순차 25%, 겹침 4%다. 융합 전처리는 순차 4.1%, 겹침 정확히
0%다. **같은 사실이다. 겹침은 호스트 작업을 싸게 만드는 게 아니라 안 세게 만든다.**

그리고 융합 경로가 무엇을 위한 것인지도 정리된다. 처리량 최적화가 아니고, 더 잘
측정해도 처리량이 되지 않는다. **지연과 메모리 트래픽** 최적화다. 중간 버퍼 셋과
프레임당 약 1.8 MB다. 그건 W5가 경주 대신 세도록 만든 항목이다.

## 측정 불가로 기록한 것

마지막 오후에 쌍 측정 다섯이 연속으로 자기 통제를 깼다.

| 실행 | 채택된 쌍 | 통제 CV | 처리량 CV |
|---|---|---|---|
| `--fused` 순차 1080p | 2/6 | 49% | 41% |
| `--fused` 겹침 360p | 1/6 | — (쌍 하나) | 38% |
| `--fused` 겹침 1080p | **0/6** | **74%** | 57% |

1080p 겹침 셀은 같은 설정의 쌍끼리 처리량이 110에서 334 FPS를 오갔고, 한 실행의
드리프트 비율이 2.05까지 갔다. 파일은 `results/`에 **"쓸 수 없음" 라벨을 달아**
남겼다. 조용히 버리지 않았다. 그 안에 든 건 플래그가 아니라 노트북을 설명한다.

**이건 어느 실험의 속성이 아니라 측정 창의 속성이다.** 그리고 W5를 다음에 하라는
가장 강한 논거이기도 하다. 주요 산출물이 개수인 단계는 이 기계에 전혀 의존하지
않는다.

잃은 건 확인뿐이다. 이 실행들이 묻던 질문에는 상한 계산이 이미 답했다. 참값이 0인
효과를 CV 57%로 재고 있었으니 실패한 측정이 확인해 줬을 것도 "0이 맞다"뿐이다.
**그리고 그 실패 자체가 논거다.** 상한을 먼저 계산했으면 세 시간을 안 썼다.
