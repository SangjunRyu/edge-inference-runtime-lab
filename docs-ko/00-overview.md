# 프로젝트 개요

원문: [`README.md`](../README.md)

추론 파이프라인의 실행 모델을 연구한 것이다. 오픈소스인
[DEEPX DX-APP](https://github.com/DEEPX-AI/dx_app) 런타임의 아키텍처에서 출발해,
평범한 하드웨어 위에서 ONNX Runtime으로 재구현했다.

DX-APP은 모델마다 동기 러너와 비동기 러너를 함께 싣고, Read / Preprocess /
Inference / Postprocess를 각각의 행으로 보고하며, 두 러너에 서로 다른 지표 타입을
유지한다. 동기에는 `ProfilingMetrics.get_fps()`, 비동기에는
`AsyncProfilingMetrics.get_throughput()`와 큐 깊이다. **이름이 다른 건 우연이
아니다.** 이 저장소는 왜 그런지를 알아낸 기록이다.

## 질문의 순서

| 단계 | 질문 |
|---|---|
| [W1](01-w1.md) | 프레임 하나는 시간을 어디에 쓰는가 |
| [W2](02-w2.md) | 스테이지를 겹치면 무엇이 달라지는가 |
| [W3](03-w3.md) | 처리량이 올라도 출력이 여전히 맞는가 |
| [W4](04-w4.md) | 같은 파이프라인을 명시적 C++ 동시성과 메모리 소유권으로 표현할 수 있고, 그 통제가 파이썬으로는 닿지 않는 개선을 드러내는가 |
| [W5](05-w5.md) | 파이프라인은 일을 거절할 수 있으려면 무엇을 소유해야 하고, 거절에는 얼마가 드는가 |

## 무엇을 알아냈는가

도달한 순서대로다. 전부 발열이 불안정한 노트북 한 대에서 측정했고, 그래서
[측정 규율](08-protocol.md)이 숫자만큼 중요하다.

**1. 겹침은 추론이 호스트가 아닌 곳에서 돌 때만 값을 한다.** NPU 1080p에서 파이프라인
러너가 순차의 **3.09배**에 닿는다. 스레드를 고정한 CPU에서는 **0.85배**로 진다.
`run_async`가 계산을 수행하는 바로 그 intra-op 풀에서 실행되므로, 동시 요청이 병렬성을
더하지 않고 나눈다. → [W2](02-w2.md)

**2. 이득의 크기는 스테이지 균형이 정하고, 순차 측정이 그걸 예측한다.**
`sum(stages) / max(stage)`가 파이프라인이 존재하기도 전에 NPU 360p에 대해 1.39배를
줬고 실측이 1.44배로 돌아왔다. 같은 상한이 CPU 360p는 겹칠 가치가 없다고 했고
실제로 그랬다. → [W1](01-w1.md)

**3. 스테이지 표의 "inference"는 장치 시간이 아니다.** 모델은 항상 224×224를 보는데
소스 해상도에 따라 74% 오른다. 오프로드 장치에서 `session.run()`은 복사와 제출과
**대기**를 포함하기 때문이다. `openvino/CPU` 행이 그걸 증명하는 통제다. 제출·대기
경로가 없고 격자에서 가장 평평한 행이다(CV 1%). → [W1](01-w1.md)

**4. 재정렬 버퍼는 후처리를 동시에 하는 값이지 DX-APP 설계의 우연이 아니다.** 수집기
하나는 순서를 어길 수 없고 버퍼도 필요 없다. 넷이면 순서를 벗어난 완료가 96개
생기고, 버퍼를 끄면 **479프레임 중 72개가 잘못된 순서로 나오면서 프레임 개수는 정확히
맞는다.** 총계까지 맞는 조용히 틀린 파이프라인이다. → [W4](04-w4.md)

**5. 파이썬 오케스트레이션은 순차에서 약 25%, 겹침에서 4% 든다.** 호스트 스테이지는
어느 쪽이든 C++이 2~10배 빠르다. 겹침이 그것들을 임계 경로에서 치우고, 임계 경로에
없는 비용은 비용이 아니다. 이건 결과 1이 반대 방향에서 도착한 것이다. **겹치는 이유는
호스트가 느려서가 아니라 호스트가 더 이상 중요하지 않게 되기 때문이다.**
→ [W4](04-w4.md)

**6. 튜닝 후보 하나는 살고 하나는 죽었다.** 전처리 다섯 패스를 하나로 융합하는 건
실재한다(1080p B/A 0.61, 방향 두 번 확인). 입력 텐서를 한 번만 바인딩하는 건 추론을
2% 움직이는데 산포가 25%다. **주변 잡음보다 작아서 지지되지 않음으로 기록했다.**
→ [W4](04-w4.md)

W5가 더한 것들이다.

**7. 동시성은 자원과 스케줄러 구조가 함께 묶는다.** 상한은
`min(버퍼 수, S + ΣQi + ΣWj)`이고, 16개 구성에서 15개가 도달했고 초과는 없었다. 어느
노브도 단독 답이 아니다. 버퍼를 늘려도 구조에 자리가 없으면 아무것도 못 사고, 큐를
깊게 해도 풀에 여유가 없으면 마찬가지다. → [W5](05-w5.md)

**8. 정렬 단위는 바이트가 아니라 요소 개수를 센다.** `align(4000, 64)`는 4,032인데
파일은 4,096이라고 한다. `align(1000, 64) × 4`다. 자체 테스트가 계획서에 이미 사실로
적혀 있던 문장을 반증했다. → [W5](05-w5.md)

**9. 블로킹은 처리량을 사지 않고 신선도를 판다.** 네 정책이 전부 같은 40 FPS를 내는데
`block`의 p95 나이가 1,921 ms로 `drop-oldest`의 100 ms보다 19배다. 그리고 **무한 큐는
존재할 수 없다.** 버퍼를 소유하는 파이프라인에서는 풀이 이미 승인 제어다.
→ [W5](05-w5.md)

**10. DX-RT의 소박한 전치 폴백은 자기 모델 입력 크기에서 합리적인 선택이다.** 소스만
읽으면 성능을 남겨둔 것처럼 보이는데, 실제 형상(157KB)에서 교과서적 블록 전치가 1.5배
**느리다.** 약 1MB 위부터 이긴다. → [W5](05-w5.md)

## 측정을 어떻게 방어하는가

기계가 스스로 10~30% 움직이므로 계측기가 작업의 대부분이다. 자세한 내용은
[측정 규율](08-protocol.md)에 있고, 요점만 적으면 이렇다.

- 모든 비교는 **쌍**이고, 비율은 **쌍 안에서** 형성한다. 쌍 안의 순서도 교대한다.
- **양쪽이 바꾸지 않는 통제 스테이지**를 두되 수준이 아니라 **분산**으로 판정한다.
  정직한 통제가 없으면 도구가 그렇다고 말한다.
- **양쪽이 정상 상태에 도달한 쌍만** 세고, 모든 쌍의 수치를 함께 출력한다.
- **쌍 하나는 아무것도 주장하지 않는다.**
- **정확성이 속도를 막는다.** 순서를 어긴 실행에는 속도 향상을 보고하지 않는다.
- **저장된 실행을 다시 읽을 수 있다.** `--reanalyse`가 기계 시간 0으로 오늘의 기준을
  적용한다. 기준이 전부 실행 이후에 고쳐졌기 때문에 중요하다.

발견한 결함은 전부 [재현 프로그램](06-repro.md)으로 남아 있다. 각각 `--mode broken`과
`--mode fixed`를 받고 그 모드가 예측한 대로 동작하면 종료 코드 0이다. 현재 11개 중
9개가 `ok`, 2개는 조건이 더는 발동하지 않아 `NOT REPRO`이고, 표가 그렇다고 말하지
통과로 반올림하지 않는다.

## 지키지 않고 철회한 것

스테이지 점유율에 대한 교차 검증(실재하는 개선을 전부 결함으로 표시했을 것이다),
이득을 원시 CV와 비교하는 무릎 검정, 교차 축 효과를 격자 최악 셀과 비교하는 요약,
"타이머들이 2% 안에서 일치한다"(쌍 하나, 우연), 그리고 CPU 대 NPU "4~6배"(1.46배
엔진 페널티 위에 3.3배 장치 이득을 쌓은 값이었다).
