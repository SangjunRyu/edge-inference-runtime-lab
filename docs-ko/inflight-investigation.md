# 요청 4·8 성능 저하 조사

## 기존 기록에서 확인한 사실

기존 요청 4 실행은 31.76 → 21.37 → 14.49장/s로 느려졌고, 이어진 요청 8은 16.24 → 18.88 → 24.22장/s로 회복했습니다. 요청 4의 두 번째 반복은 E2E 첫 10% 평균 328ms, 마지막 10% 622ms로 같은 실행 안에서도 약 1.90배 증가했습니다. Read·전처리·후처리는 비교적 비슷했고 추론 제출→callback 시간과 대기가 커졌습니다. 동일 요청 수에서 시간에 따라 변하는 현상이므로 요청 수 4·8만의 고정 특성으로 보기 어렵습니다.

기존 sweep은 조건을 0→1→2→4→8→16→32 순서로 실행했고 GPU 클럭·온도·clock event를 연속 기록하지 않았습니다. 따라서 그때의 정확한 원인이 thermal throttling, power limit, 외부 부하, runtime 실행 상태 중 무엇인지 기존 기록만으로 확정할 수 없습니다.

## 재측정 조건

같은 Imagenette 이미지 200장, warmup 20장, 조건당 3회, 파일+디코딩 모드, ORT threads=4, queue size=4입니다. 각 실행은 새 프로세스·새 세션을 사용하고 실행 사이 5초를 두었습니다. 순서는 [4,2,16,8], [8,16,2,4], [16,4,8,2]로 바꾸었습니다. 이전 300장 연속 반복과 길이가 달라, 재측정 목적은 고정된 4·8 저하의 재현 여부 확인입니다.

NVML로 SM/메모리 클럭, GPU 온도·사용률·clock event를 100ms마다 기록했습니다. 전력 사용량 API는 이 장치에서 지원되지 않아 null로 남겼습니다. CPU 사용률도 기록했으며, 아래 telemetry는 각 실행 시간의 중앙 80% 샘플입니다.

## 재측정에서 확인한 상태

12개 실행 모두 중앙 구간에서 SW Thermal Slowdown bit(0x20)가 관측됐습니다. GPU 최고 온도는 80~82°C였고, SM 클럭 중앙값은 실행에 따라 759~1,582MHz로 달라졌습니다. 같은 요청 16에서도 1,215MHz/34.46장/s와 759MHz/24.30장/s가 관측됐습니다. 같은 요청 4도 1,582MHz/42.57장/s, 1,101MHz/29.36장/s, 1,215MHz/36.84장/s로 바뀌었습니다. GPU의 열에 따른 클럭 제한이 실제로 작동했고, 클럭이 낮은 실행에서 처리율도 낮아지는 관계를 확인했습니다.

별도로 두 번째 round의 요청 8에서는 CPU 전체 사용률 평균 98.6%, Read 평균 9.55ms, preprocess 평균 11.72ms가 관측됐습니다. 같은 요청 8의 첫 round는 Read 2.24ms, preprocess 2.56ms였습니다. 해당 프로세스가 아닌 부하의 구체적인 프로그램 이름은 수집하지 않았습니다. 이는 입력·전처리 시간에도 시스템 부하가 섞일 수 있음을 보여줍니다.

따라서 기존 4·8의 이례적인 저하는 “그 요청 수 자체의 성능 특성”으로 재현되지 않았습니다. 기존의 정확한 원인은 당시 GPU telemetry가 없어 소급 확정할 수 없지만, 온도·클럭 변동과 시스템 부하가 강한 혼입 요인임은 이번 재측정에서 확인됐습니다. 이번 평균값 역시 thermal flag가 켜진 조건이 섞였으므로 새 최적 요청 수의 성능 순위로 단정하지 않습니다.

## 해석 범위

재측정 결과와 telemetry를 함께 검토해야 합니다. clock-event의 power-cap 또는 HW-slowdown 표시는 GPU가 보고한 상태이며, 그 자체로 이전 실행의 저하 원인을 확정하지는 않습니다. 특히 HW-slowdown은 고온, power-brake, 전력 보호, P-state 전환 등 여러 경우에 보고될 수 있습니다. Thermal 전용 bit와 분리해 기록했습니다.

기존 표의 “32개가 동기보다 평균 18% 빠름”은 이 조사에서 확인한 시간 변동을 포함하므로 확정적인 요청 수 최적화 성과로 사용하지 않습니다. GPU 메모리·출력 정합성 검증은 유지하되, 안정적인 성능 순위와 분리합니다.
