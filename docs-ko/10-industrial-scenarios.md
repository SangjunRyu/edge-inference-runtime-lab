# 카메라 입력의 기한과 최신성 — 트리거 검사와 스트리밍 계수 실험

> 과거 모사 실험 기록이다. 버스 이미지를 이동시키는 입력 생성·실험 실행·렌더링 코드는 제거했다.
> 현재 실행 방법과 해석은 [실제 영상 실험](11-real-video.md)을 따른다.
> 아래 수치는 실제 카메라나 공장 제품의 검증 결과가 아니다.


실행일: 2026-11-18 (Asia/Seoul). 환경: i7-8565U / GeForce MX150 2GB / RAM 8GB, ONNX Runtime 1.26.0, Python OpenCV 5.0.0.

## 실험의 질문

모델을 최대 FPS로 돌리는 데서 나아가 외부 카메라 시계가 주는 입력을 정해진 시간 안에 처리할 수 있는지 검증했다. 제조 검사에서는 누락된 제품 요청을 명시해야 하고, 연속 모니터링에서는 오래된 프레임을 보존하는 것보다 최신 결과가 중요할 수 있다는 차이를 두 계약으로 만들었다.

1. **트리거 이미지 검사:** 가상 카메라 4개가 동시에 JPEG를 제출. ResNet50 분류, 총 8 / 48 요청/초, 판정 기한 200ms, 대기 큐 4개. 가득 차면 새 요청을 명시적으로 거절한다.
2. **스트리밍 탐지·추적·계수:** YOLO11n FP32 320×320 + letterbox + NMS + 순서 복원 + centroid tracking + 라인 통과 계수. 5 / 120 프레임/초, 최신성 기한 100ms, 큐 8 / 2개, in-flight 1 / 4, 신규 거절 / 오래된 대기 프레임 폐기 비교.

200/100ms는 실험 전에 정한 예시 요구사항이다. 실제 생산라인의 센서·벨트·액추에이터에서 얻은 값이 아니다. 120 FPS는 이 모델의 예비 처리율 약 60 FPS를 넘도록 정한 가상 카메라 부하이며 실제 카메라 스펙 측정값이 아니다.

## 구현과 검증 범위

- Python orchestration + 실제 ONNX Runtime 1.26 CPU/CUDA 추론. 이번 시나리오 suite는 기존 C++ runner를 수정한 언어 비교가 아니다.
- 카메라의 예정 시각, 실제 도착, 입장/거절/교체, 추론 완료, 순서가 복원된 응용 출력 시각을 분리했다. 입력 스레드는 추론을 기다리지 않는다.
- 출력 나이(age)는 응용 출력 시각 − 예정 촬영 시각. 소스 지각·큐·전처리·추론·후처리를 모두 포함한다.
- 모든 입력 ID는 완료 또는 드롭으로 정산하고, 큐 및 active permit 상한과 출력 순서를 검사했다.
- 최종 결과는 21조건 × 2회 = 42회. 트리거 검사 완료 1,597건은 카메라별 동기 기준의 top-5 및 확률과 일치했다.
- 계수 26회 × 세 이벤트 = 78개를 정답의 통과 시각과 1:1 대응시켰다(허용 오차 0.5초, 정답 시간 해상도 1/30초). FP 0, FN 0. 최종 총계만 맞는지 확인한 것이 아니다.
- 큐 정책·좌표 복원/NMS·중복 계수·역순 콜백·독립 입력 시계·같은 총계 속의 오검출/누락에 대한 7개 테스트 통과.
- 시작 전 유휴 기준 미통과 실행 2/42회. 모든 실행의 소스 지각과 카메라별 결과를 원시 기록에 남겼다. 두 반복의 탐색 실험이므로 생산 SLA나 통계적 확정 수치로 취급하지 않는다.

## 트리거 검사 결과

각 셀은 2회 실행의 중앙값. 기한 준수율의 분모는 드롭을 포함한 전체 예정 입력이다.

| EP | 입력 요청/초 | 모드 | 요청 수/회 | 완료 수 중앙값 | 거절률 | 전체 입력 중 200ms 내 판정 | 출력 나이 p95 |
|---|---:|---|---:|---:|---:|---:|---:|
| cpu | 8 | sync | 48 | 48.0 | 0.0% | 63.5% | 273.3ms |
| cpu | 8 | async | 48 | 48.0 | 0.0% | 45.8% | 329.2ms |
| cpu | 48 | sync | 288 | 97.0 | 66.3% | 1.2% | 339.4ms |
| cpu | 48 | async | 288 | 108.0 | 62.5% | 1.0% | 529.6ms |
| cuda | 8 | sync | 48 | 48.0 | 0.0% | 95.8% | 191.1ms |
| cuda | 8 | async | 48 | 48.0 | 0.0% | 92.7% | 232.9ms |
| cuda | 48 | sync | 288 | 174.5 | 39.4% | 59.2% | 181.5ms |
| cuda | 48 | async | 288 | 227.0 | 21.2% | 64.8% | 218.5ms |

평균 입력 8건/초에서는 모든 요청을 처리했지만 네 카메라의 동시 burst로 인해 CPU의 200ms 기한 준수율은 동기 약 64%, 비동기 약 46%였다. 평균 처리 용량과 제품별 응답 기한이 다르다는 사례다. CUDA 과부하에서는 비동기가 더 많은 요청을 완료했지만 거절과 지연은 여전히 남았다. 카메라가 실제로 같은 시각에 촬영하는지, 기한이 200ms인지에 따라 답이 바뀐다.

## 스트리밍 결과

드롭률은 전체 예정 입력 대비, 기한 준수율도 전체 입력 대비다. 5 FPS는 10초에 50프레임, 120 FPS는 1,200프레임을 제공한다. 기한을 넘긴 결과도 완료 수에는 포함된다.

| EP | 입력 FPS | 모드 | 깊이/큐 | 정책 | 완료 수 중앙값 | 드롭률 | 전체 입력 중 100ms 내 출력 | 출력 나이 p95 | 계수 |
|---|---:|---|---|---|---:|---:|---:|---:|---|
| cpu | 5 | sync | 1/8 | reject-newest | 50.0 | 0.0% | 100.0% | 57.7ms | 3,3 |
| cpu | 5 | async | 4/8 | reject-newest | 50.0 | 0.0% | 100.0% | 59.3ms | 3,3 |
| cpu | 120 | async | 1/8 | reject-newest | 480.0 | 60.0% | 0.5% | 223.5ms | 3,3 |
| cpu | 120 | async | 1/8 | drop-oldest | 472.5 | 60.6% | 38.8% | 91.0ms | 3,3 |
| cpu | 120 | async | 4/8 | drop-oldest | 563.0 | 53.1% | 3.2% | 168.3ms | 3,3 |
| cuda | 5 | sync | 1/8 | reject-newest | 50.0 | 0.0% | 100.0% | 59.2ms | 3,3 |
| cuda | 5 | async | 4/8 | reject-newest | 50.0 | 0.0% | 100.0% | 36.2ms | 3,3 |
| cuda | 120 | async | 1/8 | reject-newest | 560.0 | 53.3% | 0.8% | 222.3ms | 3,3 |
| cuda | 120 | async | 1/8 | drop-oldest | 545.0 | 54.6% | 44.8% | 88.2ms | 3,3 |
| cuda | 120 | async | 4/8 | drop-oldest | 552.0 | 54.0% | 0.5% | 161.3ms | 3,3 |
| cuda | 120 | sync | 1/8 | reject-newest | 580.0 | 51.7% | 0.7% | 165.4ms | 3,3 |
| cuda | 120 | async | 4/8 | reject-newest | 515.5 | 57.0% | 0.5% | 321.6ms | 3,3 |
| cuda | 120 | async | 1/2 | drop-oldest | 532.5 | 55.6% | 44.3% | 36.7ms | 3,3 |

정상 5 FPS는 모든 입력을 기한 안에 처리했다. CUDA 120 FPS 과부하에서 깊이 1/큐 8의 신규 거절 정책은 p95 약 222ms였고 오래된 대기 프레임 교체는 약 88ms였다. 큐를 2로 줄인 최신 유지 정책은 약 37ms였다. 각각 약 53/55/56%의 입력을 버렸으므로 무손실 성능 향상으로 표현하면 안 된다. 큐를 줄여 남긴 결과의 최신성을 선택했다.

## 정확성 검사에서 발견한 CUDA 동시 요청 문제

초기 실험은 계수 총합과 순서가 맞았지만 별도 동기/비동기 출력 비교에서 일부 YOLO 박스 좌표가 달랐다. 다음 통제를 통해 범위를 좁혔다.

- CPU depth 4: 32프레임 불일치 0. CUDA depth 1: 32프레임 불일치 0.
- 기본 stream 설정의 CUDA depth 4: 출력 배열을 복사해도 32개 중 2개 불일치, raw 최대 차이 약 212. 따라서 단순 Python 배열 수명 문제만으로 설명되지 않았다.
- CUDA EP의 `use_ep_level_unified_stream=1`: 64프레임씩 3회, 총 192개 raw 출력이 동기 결과와 일치(관측 차이 0). 별도 fixed 재현 검사 64개도 통과했다.
- 기본 설정의 broken 재현 검사는 실제 불일치를 다시 검출했다. 재현 도구는 발생하지 않는 경우 NOT REPRO를 보고하며 무조건 통과로 처리하지 않는다.
- 최종 CUDA 스트리밍 16회는 이 설정으로 재측정했다. 초기 CUDA 스트리밍 숫자는 최종 표에 섞지 않았다. 나머지 CPU/ResNet 조건 26회는 설정이 바뀌지 않은 원래 측정이다.

이 통제는 이 모델·GPU·런타임 조합에서 공유 stream이 문제를 막았다는 근거다. ORT나 드라이버 내부의 정확한 결함 위치를 입증한 것은 아니다. 공유 stream에서는 여러 GPU 커널의 병렬성을 주장하지 않으며 CPU 전·후처리와 추론을 겹치는 파이프라인은 유지된다. [ORT CUDA 옵션 설명](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html#use_ep_level_unified_stream).

## 현실성의 경계

- 카메라·센서·컨베이어는 가상이다. JPEG 입력은 공개 버스 이미지의 서로 다른 crop이며 ResNet50은 제품 불량 모델이 아니다.
- 계수 영상은 공개 이미지에서 자른 버스를 움직인 통제 장면이다. 세 물체의 궤적 정답을 아는 장점이 있지만 가림·복잡한 배경·제품 다양성·카메라 진동이 없다.
- 버스 탐지와 세 이벤트의 일치를 실제 제품 계수 정확도 또는 불량 판별 정확도로 일반화하지 않는다. 전체 객체 검출 mAP 평가도 수행하지 않았다.
- 물리적 라인 통과부터 액추에이터까지의 기한은 프레임 최신성 기한과 다르다. 이벤트 보고 시각의 지연도 별도 JSON에 저장했으며 센서 보정 없이 실제 액추에이터 성능을 주장하지 않는다.
- 실제 DEEPX SDK/장비/양자화/컴파일 결과를 측정하지 않았다. 공개된 [DX-APP](https://github.com/DEEPX-AI/dx_app)의 입력·processor·async runner·후처리·tracker 분리를 참고한 독립 ORT 실험이다.

## 이 실험에서 확인한 것

“외부 시계가 입력을 주는 두 워크로드를 만들고 처리량과 제품/프레임의 기한을 구분했다. 요청별 정산과 콜백 순서·값 검증을 추가했다. 과부하에서 입장 정책·큐·in-flight를 비교했으며 계수 총합으로는 발견되지 않는 CUDA 동시 요청의 좌표 불일치를 재현하고 검증된 설정으로 다시 측정했다.”

이후 실제 제품 데이터와 라벨, trigger timestamp, 벨트 속도/제품 간격, 허용 거절률 및 액추에이터 기한을 넣으면 현장별 실험으로 구체화할 수 있다.
